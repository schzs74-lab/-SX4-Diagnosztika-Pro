# Continuous read-only measurement and clear-outcome follow-up

## Phone workflow

Build28's foreground-only live view and manual CSV recording remain available. The new **Folyamatos mérés és rögzítés indítása** action is the explicit mode for screen-off/background recording. In REAL mode, connect and select the responder first; the action closes the old foreground session and creates a new service-owned connection to that adapter and source. Select the desired polling profile before starting. DEMO uses labelled synthetic samples, with no adapter connection.

The foreground service owns its Elm327 instance, network callback, serialized polling worker and CSV writer. It holds a bounded partial CPU wake lock and Wi-Fi lock while active, displays an ongoing notification with a **stop and save** action, and can also be stopped in the app. The activity only reads bounded immutable snapshots; it neither owns nor closes the continuous recorder. Activity backgrounding, screen-off and recreation therefore do not deliberately stop this mode. Normal diagnostics/ECU/profile changes are blocked until continuous recording has stopped; archived reports/files can still be viewed/shared. Notifications can be permitted at launch; denying notification permission on Android13+ may hide the notification from the drawer, so the in-app stop action remains available.

The service is non-exported, type connectedDevice, started only by an explicit visible user action. There is no boot receiver, sticky restart, automatic reconnect or automatic resume after process death. A new run requires a new user start. No ECU writes occur in continuous mode. App removal from recents is not a stop request; the notification stop action remains available. Android force-stop/process death may leave an incomplete .part file, which is not shown as a completed recording.

Wi-Fi loss, transport loss, file errors, user stop, the CSV row/size limit or a 60-minute session cap end the session. The worker closes/syncs the file before the normal service teardown releases resources. The history is at most 60 seconds/1024 events. REAL mode requires the previously selected source to respond after the fresh connection; another source is not substituted. The source address alone does not establish unique vehicle identity.

## Actual sampling and operating context

The existing conservative 200ms inter-request delay remains unchanged. No timing optimization or additional ELM configuration is assumed to improve the adapter. Successful receive timestamps determine per-channel sample rate over the available intervals in a trailing 10-second window; fewer than two samples means insufficient data, not an invented speed. Request duration, cumulative per-channel response errors and sample age are exposed. Values are sampled separately, never made to appear simultaneous.

The fast continuous profile interleaves supported RPM (010C) and fuel-system status (0103) with three pairs of supported B1S1/B1S2 reads. Missing context PIDs are not queried/invented. Context is usable for at most five seconds; failed context reads invalidate their last value. Full-profile context may expire if the adapter is slow. The raw oxygen voltage, including A=FF => 1.275V, is retained unchanged. Open-loop status, stopped engine or absent fresh context do not turn a correctly decoded voltage into a malformed sample. They qualify interpretation without declaring the sensor or catalyst faulty. This is not an oscilloscope or catalyst pass/fail assessment.

CSV schema2 preserves the first 14 columns from schema1 and appends rate_hz, request_ms, channel_errors, rpm, rpm_age_ms, fuel_status, fuel_age_ms, context. These context ages are receive-time ages. ERROR records still have empty measured value/payload. Completed foreground recordings can also carry telemetry where available; an old oxygen-only foreground profile may lack RPM/fuel context. Numeric text uses decimal point without scientific notation; UTF8 BOM, CSV escaping and formula protection remain. Missing telemetry (including END rows) stays blank. REAL and DEMO remain distinct.

## Uncertain clearing results

Before sending Mode04 the app durably records attempt UUID, selected source, protocol, opaque connection ID and UTC time. A previous unresolved attempt cannot be overwritten by another attempt. A successful DTC read, even from the same address, does not resolve it: without unique vehicle identity this cannot prove the earlier write's outcome. The warning survives reconnects/restarts and shows its original source/time. **Korábbi törlési kísérlet áttekintése** allows explicit acknowledgement of the uncertainty; this archives the unknown outcome, not a successful-clear claim. Legacy unscoped warnings are reviewable too. Up to 20 prior journal entries are retained.

Only an exact ACK from the selected sole responder resolves an attempt as acknowledged. A recognized terminal negative reply (7F 04 with NRC11/12/13/22/31/33) from that sole responder is recorded as rejected. Response-pending NRC78, unknown codes, malformed/mixed-source replies and lost acknowledgements remain uncertain with no retry. Existing permit freshness, source/session binding, topology, fresh-DTC and stopped-engine/standstill guards remain in place. If interruption happens after dispatch is journalled but before it is sent, the journal conservatively remains uncertain.

## Verification and remaining device work

New tests exercise actual timestamp-based rates, variable simulated request latency, expired/failed operating context, maximum voltage/open-loop preservation, error rows, cancellation before append, journal persistence and matching attempt resolution, legacy review, another ECU's fresh read, terminal rejection vs response-pending and wrong-source replies. Robolectric service tests run at API28 and API35 for notification creation, explicit stop/finalization, wake-lock release, duplicate commands and activity background/recreation. Existing tests are retained.

Robolectric is not a physical Android16 lifecycle test. The user's phone must verify notification permission behavior, screen-off for at least 20 minutes, Wi-Fi/mobile-data interaction, notification stop, app recreation, file sharing and resulting CSV completeness. No new feature is claimed vehicle-verified before that check. Device/OEM battery management or process termination can still interrupt a session. Gyári service routines, Mode06 and ECU calibration writes are outside this change.
